# План создания дашборда Индекса антикоррупционной устойчивости Кыргызской Республики (ИАУ)

Документ подготовлен на основе загруженного «Методического пособия. Методика расчёта Индекса антикоррупционной устойчивости Кыргызской Республики (ИАУ)» (НИСИ при Президенте КР, 2026) и файла с перечнем статистических индикаторов.

> **Важное замечание по исходным данным.** Приложенный CSV-файл с перечнем 57 индикаторов повреждён на уровне кодировки: все кириллические ячейки (наименования индикаторов, формулировки, пояснения) заменены символами `U+FFFD` и не подлежат восстановлению из этого файла. Читаемыми остались только коды индикаторов (`a.1.1`–`c.2.9`), иерархия блок/подблок, единицы измерения и отдельные англоязычные вставки (WBES, COFOG и др.). План ниже учитывает эту структуру (коды, блоки, веса, формулы нормирования), но для точного наполнения реестра индикаторов текстами нужен файл, пересохранённый в UTF‑8 (или с указанием исходной кодировки, вероятнее всего Windows‑1251).

---

## 1. Цель и назначение дашборда

Дашборд ИАУ — цифровая аналитическая панель, которая:

1. Автоматизирует расчёт Индекса антикоррупционной устойчивости по интегральной формуле методики (гл. 5).
2. Визуализирует результаты на трёх уровнях — национальном, региональном, ведомственном (гл. 7.2).
3. Обеспечивает мониторинг 7 функциональных блоков и 57 индикаторов, систему раннего предупреждения и тематические аналитические модули (гл. 7.5–7.6).
4. Служит инструментом поддержки управленческих решений для Администрации Президента, Совбеза, Генпрокуратуры, ГКНБ, МВД, Минфина, Счётной палаты, Нацстаткома и др. (гл. 8.2).

## 2. Формализация методики → требования к расчётному движку

Из методики выделяются 4 расчётных уровня, которые дашборд должен воспроизводить программно:

| Уровень | Формула | Комментарий |
|---|---|---|
| Индикатор (нормирование, позитивный) | `Иij = (Xij − Xmin) / (Xmax − Xmin) × 100` | рост значения = улучшение |
| Индикатор (нормирование, негативный) | `Иij = (Xmax − Xij) / (Xmax − Xmin) × 100` | рост значения = ухудшение |
| Индикатор (экспертная оценка, если нормирование невозможно) | `Иij = Eij` | шкала 0–100 вводится экспертно |
| Блок | `Бi = Σ(j=1..ni) Иij × Wij`, при `Σ Wij = 1` (взвешенное среднее; при равных весах — простое среднее `Бi = (1/ni) Σ Иij`) | агрегация индикаторов внутри блока |
| Индекс | `ИАУ = Σ(i=1..7) Бi × Wi`, при `Σ Wi = 1`, конкретно `ИАУ = Б1×0,25 + Б2×0,20 + Б3×0,15 + Б4×0,15 + Б5×0,10 + Б6×0,10 + Б7×0,05` | итоговый балл 0–100 |

Эквивалентная развёрнутая форма: `ИАУ = Σ Wi × (Σ Iij × Wij)`.

**Требования к движку:**

- Хранить для каждого индикатора: код (по классификации UNODC/ИАУ), направленность (позитив/негатив/экспертный), `Xmin`, `Xmax` (или целевое значение), весовой коэффициент `Wij` внутри блока, периодичность, источник, ответственный орган.
- Поддерживать пересчёт «снизу вверх»: индикатор → блок → индекс, с сохранением промежуточных значений (для прозрачности и аудита).
- Поддерживать версии весов и границ нормирования во времени (веса могут пересматриваться экспертной комиссией — Приложение 3 методики) без потери историчности расчётов за прошлые периоды.
- Поддерживать расчёт на 4 уровнях агрегации: национальный, региональный (область/Бишкек/Ош/район), ведомственный, локальный (организация) — гл. 2.4.
- Реализовать шкалу интерпретации результатов (90–100 — очень высокий … <40 — критический, гл. 5.5) как справочник, используемый в UI (цвета, подписи).

## 3. Модель данных (укрупнённая ER-схема)

Ключевые сущности:

- **Block** (7 блоков): код, название, вес (`Wi`).
- **Indicator** (57 показателей — паспорт по п. 4.2/4.3 методики): код, наименование, блок_id, цель, определение, источник данных, метод получения, формула расчёта, единица измерения, метод нормирования, направленность (+/−/эксперт), Xmin/Xmax, вес в блоке (`Wij`), периодичность обновления, ответственный орган, метод верификации, критерии интерпретации.
- **Entity** (объект оценки): уровень (страна/регион/ведомство/организация), тип, название, родитель (для иерархии регион→район).
- **Period** (отчётный период: год, при необходимости — квартал для промежуточного мониторинга).
- **IndicatorValue**: indicator_id, entity_id, period_id, сырое значение `X`, источник, статус верификации, комментарий, вложение (файл-подтверждение).
- **NormalizedValue**: производное значение `И` (расчётное поле или материализованное для истории).
- **BlockScore**: расчёт `Бi` по entity/period.
- **IndexScore**: итоговый `ИАУ` по entity/period + уровень интерпретации.
- **Weight/NormalizationVersion**: версионирование `Wi`, `Wij`, `Xmin/Xmax` с датой вступления в силу.
- **Alert** (система раннего предупреждения): правило, порог, индикатор/блок, entity, период, статус (гл. 7.5).
- **Agency / Region**: справочники ведомств и административно-территориальных единиц (области, Бишкек, Ош, районы) с геометрией (GeoJSON) для карты.
- **User / Role / Permission**: пользователи, роли (администратор данных, аналитик, руководитель, внешний наблюдатель, представитель ведомства-поставщика данных), права по блокам/ведомствам (RBAC).
- **AuditLog**: журнал изменений данных и весов (для объективности и воспроизводимости — принципы методики, гл. 4.4).
- **Source**: справочник источников (Генпрокуратура, ГКНБ, МВД, Минфин, Минюст, Счётная палата, ГНС, ГТС, Нацстатком, Судебный департамент, портал госзакупок, соцопросы и др. — гл. 5.8).

## 4. Функциональные модули дашборда (по гл. 7.6 методики)

| 3 | Ведомственный рейтинг | рейтинг министерств/госкомитетов/органов МСУ: устойчивость, прозрачность, коррупционный риск, эффективность профилактики, закупки, конфликт интересов, динамика жалоб, результаты аудита |
| 4 | Государственные закупки | доля конкурентных закупок, повторяющиеся поставщики, признаки аффилированности/картелей, закупки без конкуренции, дробление контрактов, нарушения и санкции |

| 6 | Обращения граждан | жалобы/сообщения о коррупции, география обращений, тематика (текстовая аналитика/NLP), динамика |
| 7 | Возврат активов | суммы, динамика, эффективность взыскания похищенных/полученных незаконно активов |
| 8 | Прогноз рисков (AI) | индекс коррупционного риска, аномалии, прогноз тенденций (модуль AI Anti-Corruption Intelligence, гл. 6) |
| 9 | Система раннего предупреждения | правила триггеров по индикаторам (гл. 7.5), уведомления ответственным органам, лента сигналов |
| 10 | Администрирование методики | реестр 57 индикаторов (паспорта), управление весами и границами нормирования, версии, журнал аудита, импорт/ввод данных, статусы верификации |

## 5. Роли пользователей и доступ

- **Суперадминистратор** — управление методикой, весами, справочниками, пользователями.
- **Оператор данных ведомства** — ввод/импорт значений индикаторов по своему ведомству, приложение подтверждающих документов.
- **Верификатор/аналитик НИСИ** — проверка, подтверждение, комментирование данных, запуск пересчёта.
- **Руководитель/ЛПР** (Администрация Президента, Совбез и т.д.) — просмотр агрегированных панелей, рейтингов, экспорт отчётов, без права редактирования исходных данных.
- **Внешний наблюдатель / публичный доступ** (опционально) — ограниченная витрина без чувствительных детализаций, если предусмотрена публикация части индекса.

Доступ разграничивается по: роли, ведомству/региону (data scoping), блоку индикаторов.

## 6. Технологический стек (рекомендация)

- **Frontend:** React (Next.js) + TypeScript, графики — Recharts/ECharts, карта — Leaflet/MapLibre с GeoJSON границ областей/районов КР, UI-кит — например Ant Design/MUI с поддержкой RU/KY локализации.
- **Backend/API:** Node.js (NestJS) или Python (FastAPI/Django) — выбор по имеющимся компетенциям команды; расчётный движок методики реализуется как отдельный сервис/модуль с покрытием юнит-тестами формул.
- **База данных:** PostgreSQL (реляционная модель индикаторов/блоков/весов), возможно PostGIS для геослоёв карты.
- **Кэш/очереди:** Redis — кэш агрегатов, очередь пересчёта при обновлении данных.
- **AI/аналитический модуль (этап 2):** Python-сервис (pandas, scikit-learn/Prophet для прогноза трендов, NLP-библиотека для анализа обращений граждан — например, spaCy/transformers с поддержкой русского и киргизского языков).
- **Аутентификация:** OAuth2/JWT, поддержка интеграции с государственной системой идентификации при наличии.
- **Инфраструктура:** контейнеризация (Docker), CI/CD, размещение в защищённом government-cloud/on-premise контуре с учётом требований к обработке чувствительных госданных.
- **Экспорт/отчётность:** генерация PDF/Excel отчётов (национальный доклад, годовой мониторинг — Приложение 4 методики).

## 7. Источники и способы получения данных

По гл. 5.8 методики: Генпрокуратура, ГКНБ, МВД, Минфин, Минюст, Счётная палата, ГНС, ГТС, Нацстатком, Судебный департамент, портал госзакупок, соцопросы населения/бизнеса, иные ГИС.

Способы загрузки данных в систему (этапно):

1. **MVP:** ручной ввод/импорт через формы и Excel/CSV-шаблоны (паспорт индикатора как валидируемый шаблон), с обязательной верификацией.
2. **Развитие:** API-интеграции с доступными государственными информационными системами (портал госзакупок, реестры), где технически возможно.
3. **Перспектива:** автоматизированный конвейер (ETL) для регулярных выгрузок + модуль AI-ACI для сложной аналитики (обращения, закупки, аномалии) согласно гл. 6.3–6.4.

## 8. Поэтапный план разработки

Этапы описаны по объёму и зависимостям работ, без привязки к календарным срокам.

### Этап 0. Подготовка данных и методологии
- Восстановить/получить корректный (UTF‑8 или с верной кодировкой) файл с полным перечнем 57 индикаторов.
- Оцифровать паспорт каждого индикатора по единому шаблону (гл. 4.2–4.3): код, блок, цель, определение, источник, формула, единица измерения, Xmin/Xmax или метод экспертной оценки, вес `Wij`, периодичность, ответственный орган, метод верификации, критерии интерпретации.
- Зафиксировать веса блоков (25/20/15/15/10/10/5%) и весов индикаторов внутри блоков (Приложение 3), проверить `ΣWij = 1` для каждого блока.
- Сформировать справочники: регионы КР (7 областей + Бишкек + Ош, районы — опционально), ведомства-источники, периоды.
- **Результат:** утверждённый цифровой реестр индикаторов (например, в виде мастер-таблицы/JSON), готовый для загрузки в БД.

### Этап 1. Архитектура данных и расчётный движок
- Спроектировать и развернуть схему БД (раздел 3).
- Реализовать сервис нормирования (прямая/обратная формулы, экспертная оценка) с юнит-тестами на граничные случаи (Xmax = Xmin, отсутствие данных).
- Реализовать агрегацию блока (взвешенное среднее) и интегральную формулу ИАУ.
- Реализовать версионирование весов/границ нормирования и историчность расчётов.
- Реализовать журнал аудита (кто/когда/что изменил).
- **Результат:** работающий бэкенд-движок, воспроизводящий формулы методики, с тестовым набором данных.

### Этап 2. Backend API и панель администрирования данных
- CRUD API для индикаторов, значений, весов, справочников.
- Формы/импорт для ввода данных ведомствами, статусы верификации, вложения документов.
- RBAC (роли и доступ по ведомству/региону/блоку).
- Триггер пересчёта показателей при обновлении данных или изменении весов.
- **Результат:** административный интерфейс для наполнения системы данными.

### Этап 3. MVP дашборда — национальная панель
- Модуль 1: итоговый балл ИАУ, шкала интерпретации, динамика по годам, разбивка по 7 блокам.
- Базовая навигация, аутентификация, ролевой доступ на чтение.
- **Результат:** демонстрируемый MVP на национальном уровне.

### Этап 4. Региональный модуль
- Интеграция GeoJSON границ областей/городов Бишкек и Ош (и районов при готовности данных).
- Интерактивная карта с цветовой индикацией и карточками региона (Модуль 2, гл. 7.3).
- Рейтинг регионов, сортировка/фильтрация.

### Этап 5. Ведомственный модуль
- Рейтинг государственных органов и органов МСУ (Модуль 3).
- Детализация по устойчивости, прозрачности, риску, профилактике, закупкам, конфликту интересов, жалобам, аудиту.

### Этап 6. Тематические аналитические модули
- Модуль 4 (госзакупки): анализ конкурентности, повторяющихся поставщиков, дробления контрактов.
- Модуль 5 (конфликт интересов): декларирование, случаи выявления, санкции.
- Модуль 6 (обращения граждан): реестр обращений, география, базовая тематическая классификация.
- Модуль 7 (возврат активов): суммы, динамика, эффективность взыскания.

### Этап 7. Система раннего предупреждения
- Конструктор правил-триггеров по индикаторам/блокам (пороговые значения, темп прироста).
- Лента сигналов, уведомления ответственным органам (email/внутренние оповещения).
- Перечень типовых сигналов из методики (гл. 7.5): рост жалоб, закупки без конкурса, повторяющиеся победители тендеров, рост финансовых нарушений, снижение прозрачности, рост нераскрытых конфликтов интересов, снижение доли э-услуг, падение доверия населения.

### Этап 8. AI-модуль (AI Anti-Corruption Intelligence)
- Прогнозирование трендов индекса и индикаторов риска (временные ряды).
- Выявление аномалий (закупки, бюджетные расходы, кадровые схемы) согласно гл. 6.4.
- NLP-анализ обращений граждан и открытых источников (базовая версия — классификация тем и тональности).
- Расчёт производных AI-индексов (гл. 6.5): риска, прозрачности органа, эффективности расследования, уязвимости, прозрачности закупок, эффективности профилактики.
- Явное разграничение: AI-результаты носят информационно-аналитический характер и не являются основанием для юридических выводов (гл. 6.7) — отразить как дисклеймер в интерфейсе.

### Этап 9. Отчётность, безопасность, качество
- Генерация годового отчёта/национального доклада (шаблон Приложения 4) в PDF/Excel.
- Аудит информационной безопасности, защита персональных и чувствительных данных, резервное копирование.
- Нагрузочное и функциональное тестирование, тестирование формул на контрольных наборах данных (сверка вручную посчитанных примеров с системой).
- Документация пользователя и администратора, обучение операторов данных.

### Этап 10. Пилотное внедрение и доработка
- Пилотный расчёт ИАУ на реальных/тестовых данных за 1–2 периода.
- Сбор обратной связи от ведомств-пользователей (гл. 8.2), корректировка UX и правил валидации.
- Подготовка к ежегодному циклу расчёта и, при необходимости, ежеквартальному промежуточному мониторингу (гл. 2.5).

## 9. Риски и меры их снижения

| Риск | Мера |
|---|---|
| Отсутствие/повреждение исходных данных по 57 индикаторам (как в текущем CSV) | Повторный запрос файла в UTF‑8/верной кодировке; параллельная ручная сверка с текстом методики |
| Разрозненность и неполнота ведомственных данных | Поэтапное подключение источников, ручной ввод как временная мера, верификация НИСИ |
| Пересмотр весов/структуры индекса экспертной комиссией | Версионирование весов и границ нормирования без потери историчности прошлых расчётов |
| Чувствительность данных (правоохранительная, финансовая статистика) | RBAC, шифрование, аудит доступа, размещение в защищённом контуре |
| Некорректная интерпретация AI-результатов как «доказательств» | Дисклеймеры в UI, ограничение AI-модуля информационно-аналитической функцией (гл. 6.7) |
| Отсутствие геоданных по районам | На старте — уровень области/Бишкек/Ош, районный уровень — по мере готовности данных (гл. 2.4) |

## 10. Критерии готовности (Definition of Done) по ключевым этапам

- **Расчётный движок:** для тестового набора данных ручной расчёт по формулам методики совпадает с результатом системы (с точностью округления).
- **MVP:** пользователь с ролью «руководитель» видит итоговый ИАУ, разбивку по 7 блокам и историю минимум за 1 период.
- **Региональный модуль:** карта корректно отображает статус всех областей и городов Бишкек/Ош согласно шкале 80–100/60–79/40–59/<40.
- **Административный модуль:** оператор ведомства может внести значение индикатора, оно проходит верификацию и попадает в пересчёт блока и индекса.
- **Система раннего предупреждения:** при превышении заданного порога по индикатору формируется сигнал и виден в интерфейсе.
